# Technical Architecture Overview

This document provides a high-level technical explanation of how the Time Delay Video Playback application works. The entire process is handled client-side in the browser, leveraging a set of modern web APIs for high-performance video manipulation.

The core data flow can be summarized as follows:
**`Camera` -> `MediaRecorder` -> `DB (IndexedDB)` -> `Player` -> `MediaSource` -> `<video>` element**

---

### 1. Video Capture (`camera.ts`)

*   The process begins by accessing the user's camera using the **`MediaDevices.getUserMedia()`** API.
*   The live video stream from the camera is then passed to a **`MediaRecorder`** instance.
*   The `MediaRecorder` is configured to slice the video into small, independent chunks (e.g., one-second intervals). This is achieved by specifying a `timeslice` value in the `start()` method.
*   Each time a chunk is ready, the `MediaRecorder` fires a `dataavailable` event.

### 2. Data Persistence (`db.ts`)

*   The video chunks (`Blob` objects) generated by the `MediaRecorder` are sent to the `DB` module.
*   This module uses the **`IndexedDB`** API to store the data. IndexedDB is a low-level, transactional, and asynchronous database in the browser, ideal for storing large amounts of data like video blobs.
*   Each chunk is stored with a timestamp, allowing for efficient retrieval later.
*   The very first chunk produced by the `MediaRecorder` is a special "initialization segment" containing codec and container metadata. This is stored separately and is essential for the `MediaSource` to begin playback.
*   In addition to video chunks, IndexedDB is also used to store session information, generated thumbnails, and user-created annotations.

### 3. Video Playback (`player.ts`)

*   The `Player` module is responsible for playing the stored video chunks in the `delayed` `<video>` element.
*   It uses the **`MediaSource` API**, which allows JavaScript to dynamically construct media streams for a video element.
*   When the player starts, it first fetches the "initialization segment" from IndexedDB and appends it to the `SourceBuffer`. The `SourceBuffer` is a component of the `MediaSource` that accepts video data.
*   Once the initialization is complete, the player periodically fetches new video chunks from IndexedDB that have been recorded since the last check.
*   These chunks are placed in a queue and appended to the `SourceBuffer` one by one. The `MediaSource` API handles the complexities of stitching these chunks together for seamless playback.

### 4. Seeking and Timeline

*   When a user clicks on the timeline, the application calculates the target time.
*   The `Player` then clears its internal buffer and fetches the relevant video chunks from IndexedDB starting from the seek time.
*   These chunks are appended to the `SourceBuffer`, allowing the video element to jump to and play from the new position. This architecture is what makes near-instant seeking possible across potentially long recordings.
